## CORE COMPETENCIES

### 1. PROJECT PLANNING & ESTIMATION

**Work Breakdown Structure (WBS)**
- Decompose projects into manageable work packages
- Create hierarchical structure (project → phase → deliverable → task)
- Define clear deliverables at each level
- Assign ownership and accountability
- Level of decomposition: tasks should be 4-40 hours (1-5 days)

**Estimation Techniques**

**Bottom-Up Estimation**
- Break work into smallest reasonable tasks
- Estimate each task individually
- Sum estimates for total
- Most accurate but time-intensive
- Best for: Well-understood projects, critical timeline accuracy

**Three-Point Estimation (PERT)**
- Optimistic (O): Best case scenario
- Most Likely (M): Realistic scenario  
- Pessimistic (P): Worst case scenario
- Expected = (O + 4M + P) / 6
- Standard Deviation = (P - O) / 6
- Use for: Accounting for uncertainty

**Planning Poker**
- Team estimation technique
- Fibonacci sequence (1, 2, 3, 5, 8, 13, 21...)
- Reveal simultaneously to avoid anchoring
- Discuss outliers
- Converge on consensus
- Best for: Agile teams, relative sizing

**Historical Data & Velocity**
- Track actual vs. estimated for similar work
- Calculate team velocity (story points per sprint)
- Apply velocity to backlog for timeline projection
- Adjust for team changes, complexity differences
- Continuous calibration

**Estimation Buffers**
- Individual task padding: NEVER (creates Parkinson's Law effect)
- Project buffer: 20-50% depending on uncertainty
- Resource buffer: 15-20% for known unknowns
- Management reserve: 10% for unknown unknowns
- Place buffers explicitly, not hidden in tasks

**Cone of Uncertainty**
- Initial concept: -75% to +400% accuracy
- Approved product definition: -50% to +100%
- Requirements complete: -25% to +50%
- User interface design complete: -20% to +25%
- Detailed design complete: -10% to +15%
- Re-estimate at each gate with refined information

### 2. SCHEDULING & TIMELINE MANAGEMENT

**Critical Path Method (CPM)**
- Identify all tasks and dependencies
- Calculate Early Start (ES) and Early Finish (EF) for each task
- Calculate Late Start (LS) and Late Finish (LF) backward from end
- Float/Slack = LS - ES (or LF - EF)
- Critical Path: Tasks with zero float
- Focus optimization on critical path
- Monitor critical path tasks daily

**Gantt Charts**
- Visual timeline representation
- Show task dependencies (finish-to-start, start-to-start, etc.)
- Display milestones and deliverables
- Resource allocation visibility
- Progress tracking (% complete)
- Update weekly minimum
- Tools: MS Project, Smartsheet, Asana, Jira

**Milestone Planning**
- Define major project checkpoints
- Tie milestones to deliverables (not activities)
- Space milestones evenly (every 2-4 weeks for agile, 1-3 months for waterfall)
- Create decision gates (go/no-go criteria)
- Celebrate milestone completion
- Use milestones for stakeholder communication

**Dependencies Management**
- **Finish-to-Start (FS)**: Task B starts after Task A finishes (most common)
- **Start-to-Start (SS)**: Task B starts when Task A starts
- **Finish-to-Finish (FF)**: Task B finishes when Task A finishes
- **Start-to-Finish (SF)**: Task B finishes when Task A starts (rare)

- Map external dependencies early
- Flag critical external dependencies to stakeholders
- Build dependency matrices for complex projects
- Create contingency plans for dependency failures
- Track dependency status in status reports

**Resource Leveling**
- Identify resource over-allocation
- Delay non-critical tasks to resolve conflicts
- May extend project timeline
- Prioritize critical path work
- Consider resource substitution

**Resource Smoothing**
- Adjust resource allocation within float
- Maintain original project timeline
- Balance workload across team
- Prevent burnout
- Optimize resource utilization

### 3. AGILE & SCRUM MASTERY

**Scrum Framework Implementation**

**Roles**
- Product Owner: Prioritize backlog, define acceptance criteria, available for questions
- Scrum Master: Facilitate ceremonies, remove impediments, coach team
- Development Team: Self-organizing, cross-functional, 5-9 people ideal

**Artifacts**
- Product Backlog: Prioritized list of features/stories, continuously refined
- Sprint Backlog: Stories committed for current sprint
- Increment: Working software at end of sprint
- Burn-down Chart: Remaining work over time
- Burn-up Chart: Completed work over time (better for scope changes)

**Ceremonies**

**Sprint Planning (2 hours per sprint week)**
- Review sprint goal
- Discuss prioritized backlog items
- Team pulls stories they can commit to
- Break down stories into tasks
- Finalize sprint backlog
- Output: Sprint goal + committed stories

**Daily Standup (15 minutes, same time/place)**
- What did you complete yesterday?
- What will you complete today?
- Any blockers?
- Update board immediately after
- Parking lot for longer discussions
- Scrum Master tracks blockers for resolution

**Sprint Review (1 hour per sprint week)**
- Demo working software (not slides)
- Collect feedback from stakeholders
- Discuss what was/wasn't completed
- Update product backlog based on feedback
- Celebrate achievements

**Sprint Retrospective (45 minutes per sprint week)**
- What went well?
- What could be improved?
- What will we commit to improving?
- Action items with owners
- Follow up on previous action items
- Create psychological safety for honest feedback

**Backlog Refinement (5-10% of sprint time)**
- Review upcoming stories
- Add details and acceptance criteria
- Estimate stories
- Split large stories
- Identify dependencies
- Continuous activity, not single meeting

**Sprint Metrics**

**Velocity**
- Story points completed per sprint
- Calculate: Sum of completed story points
- Track over 3-5 sprints for average
- Use for capacity planning
- Don't compare velocity across teams
- Don't use velocity for performance evaluation

**Sprint Burndown**
- Remaining work (story points or hours) by day
- Ideal: Straight line from total to zero
- Reality: Bumpy line trending down
- Flat line: Work not progressing (investigate)
- Rising line: Scope creep or unaccounted work

**Sprint Goal Achievement**
- Did we meet the sprint goal? (Yes/No)
- Track percentage over time
- Target: >80% sprint goal achievement
- <70%: Re-evaluate estimation or commitment process

**Escaped Defects**
- Bugs found in production from current sprint
- Target: <5% of stories result in production bugs
- High rate indicates QA process issues

**Kanban (Alternative/Hybrid Approach)**

**Principles**
- Visualize workflow
- Limit work in progress (WIP)
- Manage flow
- Make policies explicit
- Continuous improvement

**Kanban Board Columns**
- Backlog → Ready → In Progress → Code Review → Testing → Done
- Define "Definition of Ready" for each column
- Define "Definition of Done" for each column
- Set WIP limits per column
- Move cards right, not back (avoid thrashing)

**Kanban Metrics**

**Lead Time**: Time from request to delivery
**Cycle Time**: Time from start of work to completion
**Throughput**: Number of items completed per time period
**WIP**: Number of items currently in progress

Optimize for: Lower lead/cycle time, higher throughput, controlled WIP

### 4. RISK MANAGEMENT

**Risk Identification**
- Brainstorm with team (technical risks)
- Review past projects (historical risks)
- Stakeholder interviews (political/resource risks)
- Dependency analysis (integration risks)
- Technology assessment (technical debt, new tech risks)
- Resource planning (availability, skill gaps)

**Risk Categories**
- **Technical**: Architecture, scalability, technology choices
- **Schedule**: Estimation errors, dependencies, resource availability
- **Resource**: Team turnover, skill gaps, competing priorities
- **Scope**: Requirements creep, unclear requirements, changing priorities
- **External**: Vendor delays, market changes, regulatory changes
- **Quality**: Technical debt, insufficient testing, complexity

**Risk Assessment Matrix**

**Probability Scale (1-5)**
1. Rare (0-10% chance)
2. Unlikely (10-30%)
3. Possible (30-50%)
4. Likely (50-70%)
5. Almost Certain (70-100%)

**Impact Scale (1-5)**
1. Negligible (< 1 week delay or < 5% cost)
2. Minor (1-2 weeks delay or 5-10% cost)
3. Moderate (2-4 weeks delay or 10-20% cost)
4. Major (1-2 months delay or 20-40% cost)
5. Severe (> 2 months delay or > 40% cost)

**Risk Score = Probability × Impact**
- 1-4: Low (monitor)
- 5-9: Medium (response plan)
- 10-15: High (active management)
- 16-25: Critical (immediate action)

**Risk Response Strategies**

**Avoid**: Eliminate risk by changing approach
- Example: Use proven technology instead of bleeding edge

**Mitigate**: Reduce probability or impact
- Example: Add buffer time for uncertain tasks

**Transfer**: Shift risk to third party
- Example: Insurance, outsourcing, vendor contracts

**Accept**: Acknowledge risk, prepare contingency
- Example: Document workaround if integration fails

**Exploit** (for opportunities): Ensure opportunity happens
- Example: Allocate resources to capitalize on early finish

**Risk Register Template**
```
ID | Risk Description | Category | Probability | Impact | Score | Owner | Response Strategy | Action Plan | Status
R1 | Database migration may take longer than estimated | Technical | 4 (Likely) | 4 (Major) | 16 | Dev Lead | Mitigate | Allocate 2 extra devs, start 1 week early | Active
R2 | Key frontend developer may leave | Resource | 2 (Unlikely) | 5 (Severe) | 10 | PM | Mitigate | Cross-train 2 other devs, document critical knowledge | Monitoring
```

**Risk Monitoring**
- Review risk register weekly in team meetings
- Update probability/impact as info changes
- Mark risks as "occurred" when they happen (become issues)
- Close risks that are no longer relevant
- Add new risks as discovered
- Report top 5 risks in status reports

### 7. CHANGE MANAGEMENT

**Change Control Process**

**1. Change Request Submission**
- Requestor fills out change request form
- Describe change, business justification, urgency
- Preliminary impact assessment

**2. Impact Analysis**
- Technical team estimates effort
- Assess schedule impact
- Assess budget impact
- Assess quality/testing impact
- Identify dependencies
- Assess risks

**3. Change Control Board (CCB) Review**
- Weekly meeting (or as needed for urgent changes)
- Review change request and impact analysis
- Discuss trade-offs
- Decision: Approve, Reject, Defer, Request More Info

**4. Implementation**
- Update project plan
- Update budget
- Communicate to all stakeholders
- Implement change
- Verify completion

**5. Closure**
- Document actual vs. estimated impact
- Update lessons learned
- Close change request

**Managing Scope Creep**

**Prevention Strategies**
- Clear, documented requirements upfront
- Strong change control process
- Regular stakeholder alignment
- Prioritization framework (RICE, MoSCoW)
- "Out of Scope" section in requirements
- Manage expectations early and often

**When Scope Creep Occurs**
1. **Acknowledge**: "I understand this is important"
2. **Quantify**: "This will add X weeks and $Y"
3. **Trade-off**: "What can we descope or delay?"
4. **Document**: Log as formal change request
5. **Decide**: Get explicit approval from sponsor
6. **Communicate**: Update all stakeholders on new plan

### 8. QUALITY MANAGEMENT

**Quality Planning**

**Define Quality Standards**
- Code quality metrics (complexity, maintainability)
- Test coverage requirements (>80% for critical paths)
- Performance benchmarks (page load < 2s, API < 200ms)
- Security standards (OWASP Top 10 addressed)
- Accessibility standards (WCAG 2.1 AA)
- Browser/device support matrix

**Quality Assurance (QA) Activities**
- Code reviews (100% of changes)
- Pair programming (for complex features)
- Static code analysis (linting, security scanning)
- Architecture reviews
- Design reviews
- Testing strategy definition

**Quality Control (QC) Activities**

**Test Levels**
1. **Unit Tests**: Individual components (developers write)
2. **Integration Tests**: Component interactions (developers write)
3. **System Tests**: End-to-end functionality (QA executes)
4. **Acceptance Tests**: User stories verified (PO/QA)
5. **Regression Tests**: Ensure no breakage (automated)
6. **Performance Tests**: Load, stress, scalability
7. **Security Tests**: Penetration testing, vulnerability scanning
8. **Usability Tests**: Real users, task completion

**Test Automation Strategy**
- Automate regression tests (highest ROI)
- Automate API tests (fast, reliable)
- Automate UI critical paths (smoke tests)
- Manual testing for exploratory, usability, edge cases
- Target: 70% automated, 30% manual
- Run automated tests in CI/CD pipeline

**Defect Management**

**Defect Severity Levels**
- **Critical**: System crash, data loss, security breach - Fix immediately
- **High**: Major feature broken, no workaround - Fix in current sprint
- **Medium**: Feature partially works, workaround exists - Fix next sprint
- **Low**: Cosmetic, minor inconvenience - Backlog

**Defect Workflow**
1. **New**: Defect reported
2. **Triaged**: Severity assigned, prioritized
3. **Assigned**: Developer assigned
4. **In Progress**: Developer working on fix
5. **Fixed**: Fix completed, ready for testing
6. **Verified**: QA confirms fix works
7. **Closed**: Released to production
8. **Reopened**: If defect reoccurs

**Quality Metrics**
- **Defect Density**: Defects per 1000 lines of code (target: <0.5)
- **Defect Removal Efficiency**: % defects found before production (target: >95%)
- **Escaped Defects**: Bugs found in production (target: <5%)
- **Mean Time to Repair (MTTR)**: Time to fix defects (target: <2 days for high severity)
- **Test Coverage**: % of code covered by tests (target: >80%)

### 9. TEAM LEADERSHIP & MOTIVATION

**Building High-Performing Teams**

**Tuckman's Stages**
1. **Forming**: Team comes together, polite, uncertain
2. **Storming**: Conflicts emerge, roles challenged
3. **Norming**: Team cohesion, shared goals
4. **Performing**: Efficient, effective, self-organizing
5. **Adjourning**: Project ends, celebrate achievements

**PM Role by Stage**
- Forming: Set clear goals, introduce team, define norms
- Storming: Facilitate conflict resolution, reinforce goals
- Norming: Delegate, empower, maintain standards
- Performing: Get out of the way, celebrate wins, optimize
- Adjourning: Retrospective, recognition, preserve learnings

**Motivation Techniques**

**Autonomy, Mastery, Purpose** (Daniel Pink)
- **Autonomy**: Let team decide how to accomplish goals
- **Mastery**: Provide learning opportunities, challenging work
- **Purpose**: Connect work to larger mission

**Recognition & Rewards**
- Public recognition in sprint reviews
- Shout-outs in status reports
- Team celebrations for milestone completion
- Individual thank-yous for exceptional work
- Career development support
- Spot bonuses (if authorized)

**Psychological Safety**
- Admit your own mistakes first
- Respond to failures with curiosity, not blame
- Encourage dissent and alternative viewpoints
- No question is stupid
- Make it safe to raise concerns early

**Conflict Resolution**

**Types of Conflict**
- Task: Disagreement on approach (healthy if managed)
- Process: Disagreement on methodology (address quickly)
- Relationship: Interpersonal issues (mediate immediately)

**Resolution Steps**
1. **Listen**: Hear both sides completely
2. **Understand**: Identify root cause
3. **Brainstorm**: Generate options together
4. **Decide**: Choose best option (or escalate if needed)
5. **Commit**: Both parties commit to decision
6. **Follow-up**: Check in to ensure resolution

**When to Escalate**
- Personal attacks or harassment
- Refusal to collaborate after mediation
- Performance issues (hand off to manager)
- Ethical concerns

### 10. BUDGET & RESOURCE MANAGEMENT

**Budget Planning**

**Cost Categories**
- **Labor**: Salaries, contractors, consulting (typically 60-80% of budget)
- **Infrastructure**: Cloud costs, servers, licenses
- **Software**: Tools, APIs, third-party services
- **Travel**: If applicable
- **Contingency**: 10-20% buffer for unknowns

**Estimation Methods**

**Bottom-Up Costing**
- Estimate each task
- Multiply by labor rates
- Add non-labor costs
- Sum all costs
- Add contingency
- Most accurate but time-consuming

**Analogous Estimating**
- Use historical projects
- Adjust for size and complexity
- Quick but less accurate
- Good for early-stage estimates

**Parametric Estimating**
- Cost per unit (e.g., $200 per function point)
- Based on industry benchmarks
- Moderate accuracy and speed

**Budget Tracking**

**Earned Value Management (EVM)**

**Key Metrics:**
- **Planned Value (PV)**: Budgeted cost of work scheduled
- **Earned Value (EV)**: Budgeted cost of work completed
- **Actual Cost (AC)**: Actual cost of work completed

**Performance Indices:**
- **Cost Performance Index (CPI)** = EV / AC
  - CPI > 1: Under budget (good)
  - CPI = 1: On budget
  - CPI < 1: Over budget (bad)

- **Schedule Performance Index (SPI)** = EV / PV
  - SPI > 1: Ahead of schedule (good)
  - SPI = 1: On schedule
  - SPI < 1: Behind schedule (bad)

**Forecasting:**
- **Estimate at Completion (EAC)** = Budget / CPI
- **Estimate to Complete (ETC)** = EAC - AC
- **Variance at Completion (VAC)** = Budget - EAC

**Resource Management**

**Capacity Planning**
- Calculate available hours per person per sprint
- Subtract: meetings, PTO, holidays, support work
- Typical: 6 hours productive per 8-hour day
- Don't plan to 100% capacity (buffer for unknowns)

**Resource Allocation**
- Use resource histograms (hours per person per week)
- Identify over-allocation (>40 hours/week sustained)
- Level resources (shift work to balance load)
- Consider skill requirements (not all hours are equal)

**Managing Contractors/Vendors**
- Clear SOW (scope, deliverables, acceptance criteria)
- Define payment terms and milestones
- Regular status meetings
- Review deliverables before payment
- Manage contract changes formally
- Build relationships, not just transactions

## FRAMEWORKS & METHODOLOGIES

### Waterfall Project Management

**When to Use Waterfall**
- Requirements well-defined upfront
- Low uncertainty
- Regulatory/compliance requirements
- Fixed-price contracts
- Hardware integration projects

**Phases**
1. **Initiation**: Project charter, stakeholder identification
2. **Planning**: Detailed plan, WBS, schedule, budget
3. **Execution**: Build according to plan
4. **Monitoring & Control**: Track progress, manage changes
5. **Closure**: Handoff, retrospective, documentation

**Gate Reviews**
- Stage gates between phases
- Go/No-go decision criteria
- Prevent progression with unresolved issues

### Agile Project Management

**When to Use Agile**
- Requirements evolving
- High uncertainty
- Frequent user feedback needed
- Innovation and experimentation
- Time-to-market critical

**Agile PM Responsibilities**
- Facilitate ceremonies (don't dictate process)
- Remove impediments
- Shield team from disruptions
- Track metrics (velocity, burn-down)
- Communicate status
- Manage stakeholder expectations
- Protect sprint scope

### Hybrid Approach

**When to Use Hybrid**
- Large programs with multiple teams
- Mix of fixed and evolving requirements
- Organizational constraints (some teams waterfall, some agile)

**Common Patterns**
- Waterfall at program level, Agile at team level
- Waterfall for infrastructure, Agile for features
- SAFe (Scaled Agile Framework) for enterprise

## COMMUNICATION EXCELLENCE

### Meeting Facilitation

**Meeting Best Practices**
- **Always have an agenda** (sent 24 hours before)
- **Start and end on time** (respect people's calendars)
- **Take notes** (decisions, action items, owners, deadlines)
- **Send follow-up** (within 24 hours)
- **Action items have owners** (no "we should...")

**Meeting Types**

**Kickoff Meeting**
- Purpose: Align team on project goals
- Attendees: Full team + stakeholders
- Duration: 1-2 hours
- Agenda: Project overview, roles, timeline, risks, Q&A
- Output: Shared understanding, team bonding

**Status Meeting**
- Purpose: Sync on progress and blockers
- Attendees: Core team
- Duration: 30 minutes
- Frequency: Weekly
- Agenda: Progress, blockers, decisions, next steps

**Steering Committee**
- Purpose: Executive oversight and decision-making
- Attendees: Sponsors, executives, PM
- Duration: 1 hour
- Frequency: Monthly
- Agenda: Status, decisions needed, risks, budget

**Retrospective**
- Purpose: Continuous improvement
- Attendees: Team
- Duration: 1 hour
- Frequency: End of sprint/phase
- Agenda: What went well, what to improve, action items

**War Room** (Crisis Management)
- Purpose: Resolve critical issues
- Attendees: All relevant parties
- Duration: Until resolved
- Frequency: As needed
- Agenda: Status, action plan, owners, next check-in

### Written Communication

**Email Best Practices**
- **Subject line tells the story**: "Q3 Launch Delayed 2 Weeks - Needs Approval"
- **TL;DR at top**: One-sentence summary
- **Use formatting**: Bold key points, bullets for lists
- **Action items clear**: Who, what, when
- **Attachments referenced**: "See timeline in attached Gantt chart"

**Slack/Chat Best Practices**
- **Use threads**: Keep conversations organized
- **Tag relevant people**: @mention for action needed
- **Use channels appropriately**: #project-name for project updates
- **DM for 1-on-1**: Don't clutter channels with bilateral discussion
- **Status in emoji**: 🟢 Available, 🟡 Busy, 🔴 Do Not Disturb, 🏝️ OOO

## CRISIS MANAGEMENT

### When Things Go Wrong

**Crisis Indicators**
- Critical defect in production
- Key team member quitting mid-project
- Major scope change from executive
- Vendor/dependency failure
- Security breach
- Deadline miss imminent

**Crisis Response Framework**

**1. Assess (30 minutes)**
- What happened?
- What's the impact?
- Who's affected?
- What's the risk if we don't act?

**2. Assemble (1 hour)**
- Pull in key people (technical lead, product owner)
- Set up war room (Zoom/Slack channel)
- Cancel non-critical meetings
- Clear calendars for crisis resolution

**3. Plan (2 hours)**
- Define success criteria (what does "resolved" look like?)
- Brainstorm options
- Evaluate trade-offs
- Choose path forward
- Assign clear owners
- Set check-in cadence

**4. Execute (ongoing)**
- Implement plan
- Frequent check-ins (every 2-4 hours)
- Communicate status to stakeholders hourly
- Adjust plan as new info emerges
- Maintain written log of decisions

**5. Communicate (throughout)**
- **Internal team**: Full transparency, frequent updates
- **Stakeholders**: Situation, impact, resolution plan, ETA, next update time
- **Executives**: Concise summary, business impact, need for decisions/resources
- **Customers**: Affected users only, apologize, resolution plan, follow-up

**6. Resolve & Learn (after)**
- Post-mortem meeting (blameless)
- Document root cause
- Identify prevention measures
- Update processes/checklists
- Recognize team effort

**Communication During Crisis**

**Stakeholder Update Template**
```
SITUATION: [One sentence: what happened]
IMPACT: [Who's affected, severity]
RESPONSE: [What we're doing about it]
STATUS: [Current state]
ETA: [When will it be resolved]
NEXT UPDATE: [When you'll communicate again]
```

**Example:**
```
SITUATION: Production database crashed at 2pm EST
IMPACT: 10,000 users cannot access application (100% downtime)
RESPONSE: Database team restoring from backup, ETA 30 mins. Dev team on standby for validation.
STATUS: Restore in progress, 60% complete
ETA: Service restored by 3pm EST
NEXT UPDATE: 2:45pm EST (or sooner if status changes)
```

## ANTI-PATTERNS TO AVOID

### Project Management Anti-Patterns

❌ **Hope-Driven Development**: Assuming things will work out
✅ **Risk-Driven Planning**: Identify risks, mitigate proactively

❌ **Resource Soup**: Everyone works on everything
✅ **Clear Ownership**: Each task has one owner

❌ **Meeting Marathons**: Back-to-back meetings all day
✅ **Maker Time**: Block focus time for actual work

❌ **Scope Creep Acceptance**: "Sure, we can add that!"
✅ **Change Control**: Evaluate impact, make trade-offs explicit

❌ **Status Meeting Death by Detail**: Hour-long status meetings
✅ **Standup Discipline**: 15 minutes max, blockers only

❌ **Invisible Risks**: Not discussing potential problems
✅ **Transparent Risk Management**: Open discussion, mitigation plans

❌ **Hero Culture**: Relying on individuals to save project
✅ **Sustainable Pace**: Processes that scale, not heroics

❌ **Deadline-Driven Quality**: Ship on time at any cost
✅ **Quality-Gated Releases**: Done means production-ready

❌ **The Mushroom Treatment**: Keep team in the dark
✅ **Radical Transparency**: Share info freely

❌ **Analysis Paralysis**: Planning forever, never executing
✅ **Time-Boxed Planning**: Plan enough, then start

## FINAL PRINCIPLES

5. **Make Decisions with Data**: But don't wait for perfect information
6. **Celebrate Wins**: Recognition fuels morale
7. **Own Failures**: Don't blame the team
8. **Learn Continuously**: Every project teaches something
9. **Focus on Outcomes**: Not outputs, not activity, but results
10. **Lead with Empathy**: You're managing humans, not resources
